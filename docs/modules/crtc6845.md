# crtc6845 — the 6845 register file

**I/O `0x3D4`–`0x3D5`** · instance `crtc1` · clocked from `c0` (8.33 MHz) ·
[`crtc6845.vhd`](../../crtc6845.vhd)

`vga.vhd` generates fixed timing and [ignores every CRTC access](vga.md) — fine for
making a picture, and fatal for being **found**.

## The problem this solves

Nothing detects a graphics card by looking at the screen. The standard test writes a
value into a CRTC register and reads it back:

```
out 3D4h, 0Fh        select R15, cursor address low
in  al, 3D5h         save what is there
out 3D5h, 66h        write a pattern
in  al, 3D5h         does the chip remember it?
```

With nothing answering `0x3D5` the read floats to open-bus `0xFF`, the pattern never
comes back, and the program concludes there is no graphics card — **while displaying
that conclusion perfectly.** Prince of Persia refuses to start for exactly this reason.

This module is the register file and nothing else. It does not change the timing and it
does not touch `vga.vhd`. It makes the card answer for itself.

## Read semantics

On an MC6845 most registers are write-only, and reading them returns **zero** — not the
value written, and not `0xFF`:

| Register | Behaviour |
|---|---|
| `R0`–`R13` | Write only — read back as `0` |
| `R14`/`R15` | Cursor address — readable. **R14 is 6 bits**, R15 is 8 |
| `R16`/`R17` | Light pen — read only, and `0` here since none is fitted |

That asymmetry is not a limitation to work around; it is the signature detection code
looks for. A register file that helpfully echoed all eighteen registers would look *less*
like a 6845 than this one does. R14's top two bits reading back clear is likewise real —
code that writes `0x66` there and expects `0x66` is wrong on genuine hardware too.

## What it feeds

The BIOS has been writing all four of these registers since day one -- see
`set_hw_cursor` and `v_curtype` in [`xtbios_src.s`](../../tools/xtbios_src.s) -- so the
values arriving here were already correct and already live. Nothing on the software side
had to change to start using them.

| Port | Registers | Consumer |
|---|---|---|
| `CURSOR` | R14/R15 | [`vga`](vga.md) -- the **text cursor** cell |
| `CUR_TOP` / `CUR_BOT` | R10(4:0) / R11(4:0) | `vga` -- first and last cursor scanline |
| `CUR_MOD` | R10(6:5) | `vga` -- blink rate, and `01` = cursor off |
| `START` | R12/R13 | **nothing** -- wired `OPEN`, deliberately; see below |

`START` is the display start address, which is to say **hardware scrolling**. Anything
that scrolls by moving it will not scroll here, because `vga.vhd` does not consume it.

**It did once.** Honouring it made Commander Keen 4 overlap itself and shifted
Arkanoid's *text* screen — and text is where the unit is unambiguous and the arithmetic
is a single addition, so the fault was not the word-versus-cell doubling that graphics
mode makes the obvious suspect. What it actually was was never established before the
change was reverted; the likeliest candidate is that `vga` hardcodes the row length to
80 bytes while a scrolling program may be changing R1.

A start address that is honoured but lands in the wrong place is worse than one that is
ignored — software that never scrolls is unaffected by the second and corrupted by the
first. So the register is still latched here and still read back as a real 6845 does;
only the top level's port map changed, to `OPEN`.

Before wiring it in a second time, run
[`SCROLLTST`](../tools.md#scrolltst--does-the-display-start-address-land-where-it-should),
which drives R12/R13 by a known amount against a pattern whose position can be read off
the screen. The full reasoning, and the two things that have to go with it (a per-field
latch and a clock-domain synchroniser), are in
[`vga`](vga.md#no-hardware-scrolling-and-that-is-a-decision).

## Verifying

[`CRTCTEST.COM`](../tools.md) runs the same probe and prints each answer:

```
  R15 cursor low    readable   write 66 -> read 66   OK
  R15 cursor low    readable   write 99 -> read 99   OK
  R14 cursor high   6 bits     write 66 -> read 26   OK
  R10 cursor start  write-only write 55 -> read 00   OK
```

Two patterns are written to R15 because a stuck bus can match one by luck. The `0x00`
expected from R10 is as much a part of the test as the values that echo: a board that
returned `0x55` there would be answering, but not like a 6845.

Before this module existed, every line read `FF`.
